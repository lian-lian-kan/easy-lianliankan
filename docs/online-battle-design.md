# 联网对战立项评估（2026-09-23）

结论先行：**建议立项，分两期走**。MVP 用 HTTP 轮询做 1v1 实时对战（约 1~2 周级），
体验验证后再评估 WebSocket 升级。本文是立项依据，不是实施记录；开工后按轮次回填 progress.md。

## 1. 背景与缺口

- 玩法侧已有 race（人机竞速，AI 按节奏推进 `race_ai_pairs`）与 duel（同屏轮流），
  对战的"人机/线下"形态已收编；与主流连连看对战产品的差距在**真人实时对战**。
- 后端已是 FastAPI + PG16 + Redis7（backend.yml 行+分支双 100% 覆盖门禁），房间/广播的
  天然载体（Redis hash/pubsub）现成；客户端已有 web_http_bridge（HTTPRequest 桥）与
  server_sync（节流推送/云端存档 adopt）同栈经验。
- 立项前提：Godot 3.6 EOL 在 scaling.md 已列为战略决策点。若近期迁 G4，
  对战基建建议在迁移后动工（HTTP 层可先行的部分仅后端 match 域）。

## 2. 玩法设计（MVP：同盘竞速 1v1）

- 双方以**同一种子各自本地生成同一张牌盘**（行列/种类/时限一致），各自消除；
  先清空者胜，超时按剩余对数/得分判。
- 对方进度以"剩余对数"呈现——直接复用 race 的对手机器进度条与 `_fail_race_lost` 判负路径，
  把 AI tick 换成网络进度事件即可。
- 结算入既有体系：注册表加一行（`online`/类别 duel），`<id>_result/_best_score/_first`
  自动派生；胜场另记 `online_wins`（平铺键走 flat_best_keys 家族约定）。
- 二期玩法：合作模式（同盘协同清空）、随机匹配池、异步对战（见 §7）。

## 3. 技术选型

| 方案 | 客户端 | 服务端 | 延迟 | 评估 |
|---|---|---|---|---|
| A. HTTP 轮询 | 零新协议，复用 HTTPRequest 桥 | /match 端点 + Redis 房间 | 0.5~1s | **MVP 推荐**：进度条粒度够用，与现有同步栈一致 |
| B. WebSocket | 新增长连接管理（重连/心跳/暂停语义） | ws + Redis pub/sub 广播 | 毫秒级 | 二期升级项：可做"对方消除动画"级同步，工作量 ~2x |
| C. WebRTC P2P | Godot 3 WebRTC + 信令服务器 | 信令仍需服务器 | 毫秒级 | 否决：服务器成本未省、复杂度最高、收益同 B |

- A 的轮询节奏：对局中 1s/次（与秒心跳同拍，复用 hud_timers 心跳），大厅等待 2s/次。
- A→B 升级路径保留：进度事件的消息形状（`{pair_left, moves, ts}`）两版通用。

## 4. 房间与同步模型

- **房间状态只存 Redis**（`room:{code}` hash：host/guest/seed/status/双端进度；
  5min TTL 由双方心跳续期），PG 只落对局结果——与"Redis 热状态 + PG 冷账本"的既有分工一致。
- **牌面不同步**：同 seed 各自生成（`seed()` 后走 create_board，成对发牌保证可解），
  服务器只收进度事件，带宽近零，牌面天然不可篡改。
- **反作弊基线（休闲级取舍）**：进度事件校验 `每消一对 ↔ moves+1` + 按理论最快消除速度限流；
  结算以双方 finish 上报对账。服务端全量模拟牌盘的强反作弊列为二期评估项，明确不做。
- **匹配**：MVP 房间码邀请（Redis SETNX 建房 + 加入），随机匹配池二期。

## 5. 客户端改动面（估）

- 对战会话：special_session 加 builder（同 seed level）+ CLASSIC_STYLE_MODES 一行；
  race 域复用为主，hud_timers 的 race tick 改为"网络进度 + AI 兜底"。
- 入口：玩法大厅 duel 分类下新增卡（注册表一行自动派生）；房间码输入/分享走 L3 弹窗
  （强上下文操作，不做页面，见 product-map 层级原则）。
- 探针：startup_probe 加 witness（建房/加入假流程）；web_entry 留根的 shell 探针补
  LIANLIAN_API_BASE 黑洞环境下的离线行为（对战入口在无后端时的降级提示）。
- 已知雷区：SW 缓存与页面生命周期（离开页面必须退出房间，防空房间占用心跳）；
  ?diag=1 诊断角标扩展一栏"对战延迟"。

## 6. 工作量与里程碑

| 里程碑 | 内容 | 估时 |
|---|---|---|
| M1 后端 match 域 | 建房/加入/心跳/进度上报/结算端点 + Redis 房间 + 测试延续 100% 门禁 | ~3 天 |
| M2 客户端对战会话 | 房间 UI、seed 同盘、进度条接入、胜负结算入注册表/成就/存档 | ~4 天 |
| M3 联调与灰度 | 弱网容错（降频/断线退出保护）、?beta=1 入口灰度、线上真机验证 | ~2 天 |
| 二期 | WebSocket 升级评估、随机匹配、合作模式、强反作弊评估 | 另立项 |

## 7. 开放问题

- **异步对战备选**：同一每日种子盘各打各的、只比分数——零实时基建（daily 基建直接复用），
  若 M1~M3 排期受阻可作为先行的低成本形态，但它不满足"实时博弈"的核心诉求，定位互补而非替代。
- Godot 4 迁移时间点（决定 M2 客户端投入是否顺延）。
- 服务成本（QPS 极低：1s 轮询 × 在线对局数；域名/HTTPS 已具备）。
- 不涉及聊天与 UGC 传输，合规面窄；对局举报/拉黑留二期。
